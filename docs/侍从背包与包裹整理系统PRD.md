- 新增严格JSON预览协议、60秒一次性令牌、逐件指纹复核、玩家级执行锁、重复执行幂等和完整背包快照响应。
- 批量结果区分成功、跳过和内部失败；存仓显示新增格、合并数量和剩余格；橙色与红色装备分解需要额外二次确认。
- 生产前端产物已通过 `npm run build` 生成，但当前服务尚未重启或部署本版本。

## 2. 背景

当前玩家可以持有丫鬟等侍从，并为侍从配置装备、物品和战斗能力。侍从背包入口已经存在，但前端初始化和消息路由不完整，玩家无法稳定查看和管理侍从物品，导致侍从装备、携带、存仓、出售和分解等玩法无法正常使用。

当前玩家背包的“整理包裹”功能也只提供逐件操作、自动合并仓库已有堆叠和硬编码杂物出售，无法满足背包物品数量增加后的管理需求。玩家缺少按道具分类、品质和具体物品进行批量出售、存仓和分解的安全工具。

本次需求需要同时解决侍从背包上下文和包裹批量整理问题，建立一套玩家与侍从可以复用、由服务端最终裁决、能够防止误操作和重复结算的物品管理体系。

## 3. 产品目标

1. 恢复丫鬟等侍从完整、稳定的背包查看和物品操作能力。
2. 明确区分玩家背包与具体侍从背包，杜绝消息、界面状态和命令目标串包。
3. 将“整理包裹”升级为独立弹窗，支持一键出售、一键存仓和一键分解。
4. 支持按道具分类、品质和具体物品组合筛选。
5. 批量执行前向玩家展示准确的命中物品、预计收益、仓库占用或分解产物。
6. 所有物品归属、操作资格、数量和结果均由服务端重新校验，前端只负责选择和展示。
7. 防止重复请求、断线重发、容量不足或执行异常造成重复收益和物品丢失。
8. 保持现有单件物品命令、物品路径、实例ID和角色存档向后兼容。

## 4. 非目标

本期不包含以下内容：

- 不重做仓库主界面、交易、拍卖、邮件附件或商店系统。
- 不新增自动定时出售、自动定时存仓或自动定时分解。
- 不允许玩家通过整理规则处理其他玩家或不属于自己的侍从物品。
- 不改变现有装备品质、精炼、镶嵌和分解产物的基础数值体系，除非实现时发现明确的现有错误。
- 不允许批量整理绕过任务物品、特殊物品、锁定、不可交易或不可分解限制。
- 不在本期建立持久化的多套整理方案；V1可以记住当前弹窗会话选择，但不要求跨设备同步方案。
- 不以直接修改 `os/` 核心引擎作为首选方案；行为增强应优先放入 `world/extends/` 和相关命令目录。

## 5. 核心术语

| 术语 | 含义 |
| --- | --- |
| 背包所有者 | 当前物品实际所属的玩家或侍从 |
| 操作者 | 发起整理或物品操作的登录玩家 |
| 玩家背包 | 背包所有者为当前登录玩家的物品容器 |
| 侍从背包 | 背包所有者为当前登录玩家名下某个侍从的物品容器 |
| 整理条件 | 道具分类、品质、包含物品和排除物品组成的筛选条件 |
| 预览 | 服务端根据当前真实背包生成可执行清单和预计结果，但尚未改动物品 |
| 执行令牌 | 服务端为一次预览生成的短期、一次性、与玩家及物品快照绑定的确认凭据 |
| 部分成功 | 批量操作中部分物品成功，其他物品因状态变化或限制被跳过，并返回明细 |

## 6. 侍从背包需求

### 6.1 入口与展示

玩家点击自己名下且位于当前场景的丫鬟或其他侍从后，可以通过“背包”入口打开侍从背包。

侍从背包至少展示：

- 侍从名称。
- 当前装备及装备部位。
- 背包物品列表。
- 背包已用格数和容量上限。
- 侍从持有银两。
- 当前查看对象明确标识为侍从，避免与玩家背包混淆。

背包为空、装备为空或部分装备槽为空时，界面必须正常显示，不能因空数组、空槽位或缺失字段报错。

### 6.2 侍从支持的物品操作

根据物品实际能力和侍从状态，侍从背包需要支持：

- 查看物品详情。
- 装备和卸下装备。
- 使用允许侍从使用的道具。
- 学习允许侍从学习的秘籍。
- 锁定和解锁物品。
- 出售物品。
- 存入主人的仓库。
- 分解装备。
- 合成可合成物品。
- 打开允许侍从打开的容器。
- 将物品交给主人，即“拿来”。
- 执行明确声明支持侍从的物品自定义动作。

不支持侍从执行的动作不得显示；不能只显示按钮后由服务端静默忽略。

### 6.3 归属与收益规则

- 侍从出售物品获得的银两归侍从主人。
- 侍从存仓时，物品进入侍从主人的仓库。
- 侍从分解装备后，分解产物进入该侍从背包。
- 侍从合成或打开物品后，新产物进入该侍从背包。
- 侍从将物品交给主人时，需要同时检查主人背包容量。
- 任一操作不得修改同场景其他玩家、其他玩家侍从或当前玩家其他侍从的物品。

### 6.4 权限与状态限制

侍从操作至少需要满足：

- 侍从记录真实存在。
- 侍从的 `master` 与当前玩家ID一致。
- 侍从位于当前玩家所在场景。
- 侍从仍然存活。
- 操作符合当前战斗、忙乱、工作状态和物品自身限制。
- 物品ID存在于该侍从当前背包或装备栏。

侍从不在场、已经死亡、正在执行不允许中断的工作、正在战斗或物品已经变化时，应返回明确的中文提示。

### 6.5 实时同步与存档

- 侍从物品新增、减少、数量变化、装备、卸下和锁定状态变化后，当前侍从背包立即刷新。
- 所有侍从增量消息必须携带侍从所有者上下文，不能继续依靠“消息中是否存在名称字段”判断归属。
- 关闭侍从背包后，侍从消息不得更新玩家背包缓存。
- 同时存在多个侍从时，消息只能更新对应侍从的状态。
- 侍从物品、装备、金钱、容量和锁定状态继续使用现有角色存档结构保存。
- 重新登录或服务器重启后，侍从物品实例ID和状态保持兼容。

## 7. 整理包裹弹窗

### 7.1 打开方式

玩家点击背包底部“整理包裹”后，打开独立整理弹窗，不再直接把当前背包列表切换为内联选择模式。

整理弹窗可以作用于：

- 当前玩家背包。
- 当前正在查看且属于玩家的侍从背包。

弹窗标题必须明确显示“整理你的背包”或“整理丫鬟的背包”。

### 7.2 功能页签

弹窗提供三个页签：

1. 一键出售。
2. 一键存仓。
3. 一键分解。

切换页签时保留当前页签的筛选状态，但不同操作的选择和预览相互独立，不能把出售清单直接复用为分解清单。

### 7.3 筛选条件

每个页签统一支持：

- 道具分类多选。
- 品质多选。
- 具体物品勾选。
- 具体物品排除。
- 全选当前筛选结果。
- 清空选择。
- 搜索当前背包中的具体物品。

筛选条件只用于生成预览。真正执行时必须以服务端生成的精确物品快照为准。

### 7.4 道具分类

服务端使用稳定英文枚举，前端显示中文名称：

| 分类ID | 中文名称 | 典型内容 |
| --- | --- | --- |
| `fragment` | 武功残页 | 武功秘籍残页、武学进阶残页等 |
| `manual` | 武功秘籍 | 完整秘籍、抄本、拓本等 |
| `equipment` | 装备 | 武器及各穿戴部位装备 |
| `stone` | 宝石晶石 | 玄晶、元晶、属性晶石等 |
| `material` | 材料资源 | 药草、矿石、皮毛及制造材料 |
| `consumable` | 消耗品 | 药品、食物、可打开容器等 |
| `misc` | 杂物 | 普通可处理杂物 |
| `quest` | 任务物品 | 师门、追捕、副本和剧情任务物品 |
| `special` | 特殊物品 | 活动、付费、限时和系统特殊物品 |

分类必须由服务端集中计算。判断优先级为：

1. 物品显式声明的整理分类和保护标记。
2. 装备、秘籍、残页等明确对象类型。
3. 现有 `otype`。
4. 受控的对象路径前缀回退规则。

禁止使用中文名称包含关系作为最终分类依据。

### 7.5 品质筛选

品质选项包括：

- 白色，`grade 0`。
- 绿色，`grade 1`。
- 蓝色，`grade 2`。
- 黄色，`grade 3`。
- 紫色，`grade 4`。
- 橙色，`grade 5`。
- 红色，`grade 6`。
- 无品质，`quality null`。

当前所有基础物品默认具有 `grade 0`，因此协议必须额外提供该物品是否真正适用品质体系，不能把全部 `grade 0` 物品都显示为白色品质。

### 7.6 具体物品选择

- 具体物品列表只展示当前背包中符合分类和品质条件的物品实例。
- 相同路径的可堆叠物品按当前堆叠实例显示数量。
- 非堆叠装备按实例单独显示，保留精炼、镶嵌、锁定和品质信息。
- 玩家可以排除单个物品，排除优先级高于分类和品质筛选。
- 预览生成后新获得的物品不得自动加入本次执行。
- 预览生成后数量减少、物品转移或状态改变时，执行阶段重新校验并跳过变化项。

### 7.7 预览区域

执行前必须显示：

- 命中的物品种类数。
- 命中的物品总数量。
- 被保护或不符合条件的跳过数量。
- 一键出售的预计银两。
- 一键存仓的预计新增仓库格数、合并数量和剩余空间。
- 一键分解的预计产物及数量。
- 高风险物品名称和风险原因。

玩家未完成有效预览时，确认按钮不可用。

## 8. 一键出售规则

### 8.1 可出售条件

物品至少满足以下条件才能进入出售清单：

- 当前仍属于指定背包所有者。
- 物品允许交易或出售。
- 物品具有大于0的出售价值。
- 物品未锁定。
- 物品不在装备栏。
- 物品不是任务、剧情或受保护特殊物品。
- 装备没有不允许出售的精炼或镶嵌状态。

### 8.2 收益

- 玩家背包出售所得进入玩家银两。
- 侍从背包出售所得进入侍从主人的银两。
- 预计收益和最终收益使用同一服务端计算函数。
- 最终结果必须返回实际出售物品、数量和实际获得银两。

### 8.3 高风险保护

- 批量出售默认排除所有已精炼装备，即使现有单件出售允许低精炼装备出售。
- 已镶嵌装备禁止批量出售。
- 紫色及以上装备在预览中单独列为高风险物品，并需要额外确认。
- 红色或系统标记为不可批量出售的物品直接跳过。

## 9. 一键存仓规则

### 9.1 仓库归属

- 玩家背包存仓进入玩家仓库。
- 侍从背包存仓进入侍从主人的仓库。
- V1不建立侍从独立仓库。

### 9.2 容量计算

服务端预览时需要同时计算：

- 能够与仓库已有物品合并的堆叠。
- 需要新增仓库格子的物品。
- 仓库当前容量和剩余格数。
- 无法存入的物品及原因。

执行时再次检查仓库状态。仓库空间不足时只跳过无法存入的物品，物品继续保留在原背包。

### 9.3 保护规则

- 默认排除锁定、任务、剧情和特殊物品。
- 已装备物品不属于背包整理范围。
- 不允许存仓的限时、绑定或状态物品自动跳过。
- 存仓属于转移操作，不能销毁、复制或改变物品实例属性。

## 10. 一键分解规则

### 10.1 可分解条件

装备至少满足以下条件才能进入分解清单：

- 当前仍属于指定背包所有者。
- 物品为装备且具有有效品质。
- 物品未锁定。
- 物品未装备。
- 物品没有 `no_fenjie` 或同等保护标记。
- 物品不是任务、剧情或特殊保护装备。
- 物品没有不允许分解的镶嵌状态。
- 物品符合当前品质对应的分解规则。

### 10.2 产物预览

- 普通装备显示预计玄晶数量。
- 高品质装备显示预计元晶、属性晶石及其他产物。
- 预计产物和最终产物必须使用同一服务端计算函数。
- 侍从分解产物进入侍从背包，并按侍从容量计算。

### 10.3 容量与回滚

当前项目不能依赖物品找回功能兜底，因此必须遵守：

1. 先计算分解产物。
2. 预检目标背包能否接收产物。
3. 再次确认原装备仍存在且状态未改变。
4. 移除原装备。
5. 添加全部分解产物。
6. 任一步骤异常时，将原装备恢复到原背包并记录错误。

不允许出现“装备已经删除，但产物因背包满而发放失败”的结果。

### 10.4 高品质确认

- 紫色装备需要显示醒目风险提示。
- 橙色和红色装备需要额外二次确认，并列出每件装备名称和预计产物。
- 服务端标记为不可批量分解的装备即使品质被选中也必须跳过。

## 11. 默认保护规则

| 物品状态 | 出售 | 存仓 | 分解 |
| --- | --- | --- | --- |
| 锁定 | 默认排除 | 默认排除 | 默认排除 |
| 已装备 | 不参与 | 不参与 | 不参与 |
| 任务或剧情物品 | 禁止 | 默认禁止 | 禁止 |
| 特殊或活动物品 | 默认禁止 | 按服务端标记 | 默认禁止 |
| 已镶嵌装备 | 禁止 | 可以按普通装备存仓 | 禁止 |
| 已精炼装备 | 默认排除 | 可以按普通装备存仓 | 默认排除 |
| 不可交易物品 | 禁止 | 按服务端标记 | 按分解标记 |
| 无价值物品 | 禁止出售 | 按服务端标记 | 按分解标记 |

所有规则以服务端最终校验为准。前端隐藏按钮不是安全措施。

## 12. 协议设计

### 12.1 兼容原则

- 保留现有 `pack` 作为玩家背包入口。
- 保留并修复 `pack2` 作为侍从背包入口。
- 保留现有单件 `sell`、`store`、`fenjie`、`eq`、`uneq` 等命令。
- 新增批量整理协议，不改变旧命令参数含义。
- 新协议服务端响应使用 `JSON.stringify()` 生成严格JSON，避免手工拼接造成转义错误。
- 新协议不接受客户端提供的对象路径作为执行目标，只接受当前容器中的实例ID和服务端令牌。

### 12.2 背包上下文

玩家和侍从背包响应统一补充：

```json
{
    "protocol": 2,
    "owner": {
        "type": "player",
        "id": "playerId",
        "name": "玩家名"
    },
    "revision": 18,
    "money": 1000,
    "capacity": {
        "used": 32,
        "max": 100
    }
}
```

侍从上下文示例：

```json
{
    "owner": {
        "type": "follower",
        "id": "followerId",
        "name": "丫鬟",
        "masterId": "playerId"
    }
}
```

所有增量消息必须包含 `owner.type` 和 `owner.id`。`revision` 用于客户端判断是否需要重新获取完整快照，但执行安全不能只依赖版本号，仍需逐件验证。

### 12.3 整理物品字段

```json
{
    "id": "itemId",
    "path": "book/bc#skillId",
    "name": "武功残页",
    "category": "fragment",
    "subcategory": "skill_fragment",
    "quality": 3,
    "count": 20,
    "unit": "张",
    "value": 1000,
    "flags": {
        "locked": false,
        "equipped": false,
        "refined": false,
        "socketed": false,
        "task": false,
        "special": false
    },
    "actions": {
        "sell": {
            "allowed": true,
            "value": 20000
        },
        "store": {
            "allowed": true,
            "slots": 1
        },
        "disassemble": {
            "allowed": false,
            "reason": "NOT_EQUIPMENT"
        }
    }
}
```

`path`只用于展示、分类核对和服务端快照，不得作为客户端执行指定物品的依据。

### 12.6 执行令牌

执行令牌必须满足：

- 使用密码学安全随机数生成，不使用普通时间戳或 `Math.random()`。
- 绑定当前玩家ID、背包所有者、操作类型、物品ID、数量和关键状态快照。
- 默认60秒过期。
- 只能执行一次。
- 重复提交已经成功执行的令牌时，返回上一次执行结果，不再次处理物品。
- 服务器重启后未执行令牌自然失效，客户端提示重新预览。
- 令牌只保存在运行时内存，不写入角色存档。

断线后客户端可能重发最后一条命令，因此批量执行的幂等性是强制要求，不能只依赖按钮防重复点击。

### 12.7 执行响应

执行结果至少包含：

- 操作ID。
- 背包所有者。
- 操作类型。
- 成功物品明细。
- 跳过物品明细。
- 失败物品明细。
- 实际银两、仓库变化或分解产物。
- 最新背包完整快照。
- 存仓操作后的仓库容量摘要。

客户端收到执行结果后，以服务端完整快照覆盖当前对应背包缓存，不能只依赖一连串增量消息推算最终状态。

## 13. 错误码

| `OWNER_NOT_FOUND` | 背包所有者不存在 |

| `NOT_STORABLE` | 物品不可存仓 |

## 14. 服务端实现原则

### 14.1 公共物品管理逻辑

建议在 `world/extends/` 建立统一物品管理能力，集中提供：

- 物品分类。
- 品质适用性判断。
- 出售资格和收益计算。
- 存仓资格、堆叠和容量计算。
- 分解资格和产物计算。
- 任务及特殊物品保护判断。
- 玩家与侍从所有者解析。
- 执行结果和错误码格式化。

现有单件 `sell`、`store`、`fenjie` 和自动拾取中的出售、分解逻辑应逐步调用同一组校验和计算函数，避免不同入口产生不同结果。

### 14.2 不直接复用的旧行为

- 不直接调用 `sell all`，因为其分类为硬编码杂物规则。
- 不直接调用 `store all`，因为其只合并仓库已有的可堆叠物品。
- 不通过前端循环发送单件 `sell`、`store` 或 `fenjie` 命令。
- 不通过 `dc` 代理整个批量整理命令，避免扩大侍从代理权限。
- 不依赖当前空实现的物品找回接口恢复批量操作错误。

### 14.3 侍从命令代理

现有 `dc` 继续负责经过白名单的单件侍从动作，但需要：

- 在异常和正常路径中都清理侍从消息监听，使用等价于 `finally` 的处理方式。
- 补充经过确认的安全命令，例如锁定、打开和合成。
- 对自定义物品动作增加“是否支持侍从”的显式能力判断。
- 不能仅依赖前端按钮隐藏控制权限。

## 15. 一致性、幂等与审计

### 15.1 执行模型

批量操作采用“整批预检、逐件原子执行、允许部分成功”的模型：

- 预览尽量提前发现容量和保护问题。
- 执行时逐件重新校验。
- 单件失败不得影响其他已经安全完成的物品。
- 单件操作必须保证成功完成或物品保持原状。
- 最终返回成功、跳过和失败明细。

本期不要求对整批物品建立数据库级全有或全无事务，因为玩家物品当前保存在角色运行时对象中；但必须保证每件物品不会处于“原物品消失且结果未发放”的中间状态。

### 15.2 并发控制

- 同一玩家同一时间只允许一个批量整理执行。
- 玩家背包与其侍从背包共享操作锁，避免同时转移同一归属体系中的物品和仓库。
- JavaScript单线程不能替代业务锁，重复消息和重入命令仍需显式阻止。

### 15.3 审计记录

服务端记录：

- 操作ID和时间。
- 玩家ID和名称。
- 侍从ID和名称，若有。
- 操作类型。
- 成功、跳过、失败数量。
- 实际银两变化、仓库变化或分解产物摘要。
- 内部异常上下文。

日志不得记录登录凭证、Cookie、Session或其他敏感信息。

## 16. 前端交互要求

### 16.1 布局

整理弹窗建议分为：

- 顶部：出售、存仓、分解页签。
- 左侧或上部：分类和品质筛选。
- 中部：具体物品列表和搜索。
- 右侧或下部：命中结果、预计收益和风险提示。
- 底部：全选、清空、重新预览、取消和确认执行。

768px桌面布局可以使用左右分栏；窄屏手机改为上下布局，筛选、列表、预览和确认按钮不得相互遮挡。

### 16.2 控件

- 分类和品质使用复选框。
- 功能模式使用页签。
- 具体物品使用复选框列表。
- 搜索使用单一输入框。
- 高风险提示使用明确文字和品质颜色，不只依赖颜色区分。
- 加载、无结果、预览过期、执行中、部分成功和失败均需有独立状态。

### 16.3 防误触

- 未选择任何有效物品时禁止执行。
- 筛选条件改变后，旧预览立即失效。
- 执行期间按钮进入不可重复点击状态。
- 紫色及以上装备显示单独风险区域。
- 橙色和红色装备分解使用额外确认弹窗。
- 最终结果允许玩家展开查看跳过和失败原因。

## 17. 兼容与迁移

- 不修改现有物品路径。
- 不重建或批量替换现有物品实例ID。
- 不修改现有角色、侍从、背包、仓库和装备存档字段的含义。
- 新增的分类和操作能力优先运行时计算，不要求一次性迁移全部玩家存档。
- 旧客户端继续可以使用单件物品命令；新批量协议只在新前端入口使用。
- `pack` 和 `pack2` 的旧基础字段继续保留，新字段以向后兼容方式增加。
- 新增命令、侍从消息协议和前端模块首次生产启用需要重启游戏服务并重新构建前端。

## 18. 验证场景

### 18.1 侍从背包

- 玩家拥有一个空背包侍从。
- 玩家拥有多个侍从并依次打开不同背包。
- 侍从背包包含可堆叠道具和非堆叠装备。
- 侍从装备、卸下、锁定、解锁、使用、合成、打开和拿来物品。
- 侍从出售后银两进入主人。
- 侍从存仓后物品进入主人仓库。
- 侍从分解后产物进入侍从背包。
- 侍从离开房间、死亡、战斗或忙乱时发起操作。
- 关闭侍从背包后玩家获得新物品，玩家背包不被侍从缓存污染。
- 重新登录和重启后侍从物品及装备保持。

### 18.2 一键出售

- 按残页、秘籍、装备和杂物分类出售。
- 按单个和多个品质出售。
- 排除具体物品。
- 锁定、任务、特殊、精炼和镶嵌物品被正确保护。
- 侍从出售所得进入主人。
- 预览后物品数量变化，执行时正确跳过。
- 重复提交同一令牌不重复获得银两。

### 18.3 一键存仓

- 全部物品都能与仓库已有堆叠合并。
- 部分物品需要新增仓库格。
- 仓库恰好剩余一个格。
- 仓库容量不足导致部分成功。
- 侍从存仓进入主人仓库。
- 执行过程中物品被其他操作转移时正确跳过。

### 18.4 一键分解

- 白、绿、蓝、黄、紫、橙、红品质分别预览。
- 普通玄晶产物和高品质元晶、属性晶石产物准确。
- 锁定、镶嵌、不可分解和特殊装备被保护。
- 产物可合并时不额外占格。
- 产物无法放入时原装备保持不变。
- 侍从容量不足时不得删除侍从装备。
- 重复提交令牌不重复获得分解产物。

### 18.5 协议与异常

- 非法JSON、未知操作、未知分类和越界品质被拒绝。
- 超长请求和超过物品数量上限被拒绝。
- 伪造侍从ID和其他玩家物品ID被拒绝。
- 预览令牌过期、已使用和服务重启后失效。
- WebSocket断线后重发执行命令不重复结算。
- 执行中出现异常时物品保持或回滚，并返回完整快照。

## 19. 验收标准

满足以下条件方可认为V1完成：

1. 玩家可以稳定打开自己名下侍从的背包，控制台无初始化或方法缺失错误。
2. 玩家和侍从背包数据不会互相覆盖，多个侍从之间也不会串包。
3. 侍从支持经确认的完整物品操作，操作目标和结果归属正确。
4. 整理包裹以独立弹窗呈现，包含出售、存仓和分解三个页签。
5. 三个页签均支持分类、品质和具体物品筛选。
6. 每次批量操作都经过服务端预览、玩家确认和一次性令牌执行。
7. 锁定、任务、剧情、特殊、精炼和镶嵌保护规则有效。
8. 仓库或背包容量不足不会造成任何物品丢失。
9. 重复点击、断线重发和重复令牌不会产生重复银两、重复存仓或重复分解产物。
10. 执行结果准确显示成功、跳过和失败明细，并刷新对应背包完整快照。
11. 玩家与侍从物品、装备和锁定状态在重新登录及服务器重启后保持。
12. 前端在窄屏手机和768px桌面布局下无按钮遮挡、文字溢出或滚动区域失效。
