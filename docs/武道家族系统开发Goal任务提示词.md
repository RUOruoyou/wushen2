# 武道家族系统开发 Goal 任务提示词

将以下内容作为后续 Goal/编码代理的完整任务提示词使用。

---

## 你的角色

你是 wsmud2 项目的资深全栈开发者。你的任务不是只写设计说明，而是基于仓库现有代码，分阶段实现“武道家族系统”，并在每个阶段完成验证、兼容迁移和文档记录。

必须先阅读并遵守：

1. `/root/wsmud2/AGENTS.md`
2. `/root/wsmud2/readme.md`
3. `/root/wsmud2/PROJECT_DOC.md`
4. `/root/wsmud2/docs/武道家族系统设计方案.md`
5. 本提示词

设计方案是产品规则的主要依据；本提示词是开发执行规则。若设计方案与实际代码不一致，以实际代码为准，但必须记录差异并给出兼容实现，不得悄悄改变玩法规则。

## 总目标

把现有“随从可以参与战斗、住宅功能单一”的结构，改造成“随从永久退出战斗、成为住宅岗位成员、住宅可以扩建并进行模拟经营”的武道家族系统。

系统必须同时满足：

- 随从不能通过任何服务端路径加入战斗、自动击杀或副本队伍；
- 住宅无人值守时仍有低效率基础生产，成员值守后获得高效率、高品质、订单和事件能力；
- 首版支持挖矿、种植、炼药、授课/武馆四个职业；
- 玩家可以扩建住宅、升级房间和设施、管理仓库、排班成员、处理任务和事件；
- 成员有真实的职业成长、资质差异、特性、疲劳、心情、忠诚、培训和里程碑；
- 家族可以通过材料、资金、丹药、训练、练功房、武馆课程和声望真实提升玩家，但不提供战斗队友；
- 旧住宅、旧随从、旧命令和旧存档能够兼容迁移；
- 所有生产奖励可离线结算、可追踪、不可重复领取；
- 玩法具备模拟经营闭环，而不是单纯增加几个“工作”按钮。

## 不可改变的产品边界

### 1. 随从永久退出战斗

服务端必须阻止以下行为：

- `team with <随从>`、`team add <随从>`、队伍回复等任何入队路径；
- 对随从执行 `fight` 或 `kill`；
- 玩家攻击普通目标时，自动遍历队伍并调用随从 `do_kill`；
- 随从通过 `auto_kill`、跟随或副本复制房间进入战斗；
- 任何伪造 WebSocket 命令绕过前端后继续触发上述行为。

必须保留随从在住宅、安全区中的展示、对白、陪同和家族互动能力。不能只隐藏前端按钮，必须在对象、命令、战斗和移动路径进行服务端校验。

### 2. 家族不替代全部游戏内容

家族可以生产基础到中阶材料、成品、现金流、丹药和训练资源。副本核心掉落、顶级装备材料和关键探索内容仍由玩家获取。

家族可以提高玩家修炼效率、提供临时状态、技能熟练度、战前准备和有限的高阶课程收益，但不能生成战斗队友，也不能无限叠加攻击、防御、气血或命中。

### 3. 经营不采用过度惩罚

- 无人值守保留基础生产；成员值守决定效率、品质和高级内容；
- 维护不足先降效，再暂停高耗或高阶队列，最后才停用设施；
- 失败降低本批次品质、收益或部分投入，不删除成员；
- 疲劳、心情和忠诚可以通过休息、伙食、对话、培训和设施恢复；
- 住宅早期有发展取舍，后期允许继续扩建和补齐设施，不永久锁死路线。

遇到实现岔路时，不要把普通设计问题逐个抛回用户。先基于设计方案和现有代码自行完成一轮判断：给出一个最贴合项目的推荐，说明它解决的经营问题、代码影响和代价，然后直接采用该方案。只有当选择会破坏存档兼容、改变“随从不战斗”边界、写入生产数据或引入重大新依赖时，才暂停并请求用户决定。

## 推荐的实现边界

优先在 `world/extends/` 新增家族领域逻辑，建议建立统一的 `HOUSEHOLD` 服务或等价模块，具体加载方式必须遵循项目现有动态脚本机制，不得擅自把世界脚本改成普通 `module.exports` 模块。

建议提供以下能力，名称可按项目既有风格调整，但职责不能缺失：

```text
HOUSEHOLD.ensure(user)
HOUSEHOLD.view(user)
HOUSEHOLD.assign(user, followerId, job, options)
HOUSEHOLD.stop(user, followerId)
HOUSEHOLD.collect(user, taskId)
HOUSEHOLD.upgrade(user, target)
HOUSEHOLD.tick(user, now)
HOUSEHOLD.save(user)
```

`HOUSEHOLD` 不得调用 `do_kill`、`fight`、`team with`，不得把家族成员写入 `me.team`。

## 存档与迁移要求

### 1. 新增顶层 `household`

不要把复杂嵌套数据塞进 `temp`。建议的可序列化结构如下，字段可根据现有存档封装调整：

```js
{
    version: 1,
    level: 1,
    funds: 0,
    reputation: 0,
    rooms: {},
    facilities: {},
    members: {},
    tasks: {},
    warehouse: {},
    pendingRewards: {},
    achievements: {},
    lastTickAt: 0
}
```

成员资料至少需要支持：

- `followerId`
- `job`
- `aptitude`
- `jobLevel`
- `jobExp`
- `traits`
- `fatigue`
- `mood`
- `loyalty`
- `status`
- `milestones`
- `history`

不要重复保存随从的技能、装备和背包作为另一份权威数据。旧随从资产继续由现有 `FOLLOWER.STORES/SAVE` 负责，家族只保存经营相关资料。

### 2. 兼容旧住宅

- `temp.home=1` 映射为一级住宅；
- `temp.home=2` 映射为二级住宅；
- 没有住宅的旧角色可以打开家族面板，但不能开始生产；
- 旧字段保留，不得直接删除或改含义；
- `household.version` 迁移必须幂等，重复登录、重启和热更新不能重复发放房屋、材料或职业奖励。

### 3. 离线结算

- 统一在登录、打开家族面板、执行家族命令、退出保存前调用 `HOUSEHOLD.tick`；
- 不为每个成员建立独立定时器；
- 使用统一时间戳和任务唯一 ID；
- 首版离线结算上限建议为 72 小时，并设计为可配置值；
- 服务器时间回拨不能倒退已结算进度；
- 仓库满时进入待领取区，不丢失产物、不溢出背包；
- 重复点击领取只能成功一次。

## 首版职业和经营循环

首版只实现四个职业，使用同一套任务模型：

### 挖矿

消耗工具耐久和维护资源，产出矿石、加工材料和订单材料。成员的采矿等级、资质、工具和矿场设施影响效率和品质。

### 种植

消耗种子、土地和照料时间，产出药材、食材和特殊植物。成员影响成长速度、品质、病虫害事件和收获数量。

### 炼药

消耗药材、燃料和配方，产出恢复品、修炼辅助品和订单丹药。成员的炼药等级、特性和药房等级影响成功率、品质和副产物。

### 授课/武馆

消耗武馆维护和宣传资源，产生学费、声望、学员关系和训练机会。成员的教习能力、耐心、专长和武馆等级影响收入、课程质量和解锁内容。

每个职业必须具备：

1. 投入资源；
2. 生产周期；
3. 基础无人值守产出；
4. 成员值守后的效率、品质或内容提升；
5. 可领取产出；
6. 维护成本；
7. 至少一种事件、订单或选择；
8. 可通过成员训练和设施升级提升的长期成长。

## 住宅扩建和设施

住宅必须从 `home=1/2` 的固定标识扩展为可升级经营基地。

首版至少支持：

- 住宅等级；
- 房间槽位；
- 仓库容量；
- 矿场；
- 药圃或种植地；
- 炼药房；
- 武馆/学堂；
- 练功房或休息设施；
- 维护费用；
- 设施升级费用和前置材料。

早期房间有限，玩家需要优先选择发展方向；后期可以扩建并补齐设施。不要把路线设计成永久不可逆的职业锁定。

## 命令和兼容入口

保留 `rel <随从> <工作>` 作为兼容入口，但将其转换为家族派工，不再调用随从实时 `do_command` 工作状态。

至少支持以下行为，具体命令名沿用项目既有命令解析方式：

- 查看家族；
- 查看住宅和设施；
- 查看成员状态；
- 分派挖矿、种植、炼药、授课；
- 停止或调换岗位；
- 领取产出；
- 升级住宅、设施和仓库；
- 查看订单、事件、声望和成就。

所有命令都必须在服务端检查住宅、成员、设施、资源、容量、当前任务和权限。错误提示应说明缺少什么以及如何恢复。

## 前端要求

沿用现有 `Page`、`Dialog`、`Process`、`SendCommand` 和 jQuery 事件委托体系。

建议新增 `Dialog.household`，并在 `src/process.js` 注册服务端家族消息。关系弹窗保留旧成员摘要，但工作按钮改为打开家族面板或发送兼容派工命令。

必须做到：

- 不展示随从战斗按钮；
- 家族成员状态、岗位、疲劳、心情、任务进度、产出和升级条件可见；
- 手机窄屏和 768px 桌面布局不溢出；
- 前端操作失败时显示服务端返回原因；
- 断线重连后可以重新加载家族面板；
- 不依赖前端隐藏来保证安全。

## 推荐开发阶段

### 阶段 0：代码勘察和基线

1. 阅读 AGENTS、项目文档和设计方案；
2. 搜索随从入队、自动战斗、住宅购买、存档保存、关系面板和消息分发的完整调用链；
3. 记录现有行为和需要兼容的字段；
4. 输出不超过 20 行的短计划和风险清单，然后直接开始第一阶段；只有触及核心边界的风险才等待用户决定。

### 阶段 1：存档、HOUSEHOLD 基础和迁移

实现 `household` 默认数据、`ensure`、读取保存、版本迁移、基础 `view` 和统一 `tick`。先不接入全部职业，先证明旧角色可登录、旧住宅不丢失、重复迁移不重复奖励。

### 阶段 2：彻底切断随从战斗

修改对象、组队、战斗、自动击杀和副本移动边界；保留住宅和安全区互动。验证普通玩家队伍、非随从目标战斗和原有副本流程不受影响。

### 阶段 3：住宅设施和四个职业

实现房间、设施、仓库、维护、基础无人值守产出、成员值守加成、任务队列、离线结算、领取和停止结算。

### 阶段 4：成员培养和玩家提升

实现职业等级、资质、特性、疲劳、心情、忠诚、培训、转职、里程碑、订单、事件、武馆声望、练功房和有限战前训练收益。

### 阶段 5：前端家族面板和交互打磨

实现 `Dialog.household`、关系弹窗兼容、状态刷新、错误反馈、移动端布局和断线重连。

### 阶段 6：平衡、文档和交付

验证四条路线的投入产出、维护成本、离线收益和玩家提升；更新设计文档中的实际差异、更新 `docs/开发日志.md`；如涉及玩家可感知功能，只拟定公告，未获用户确认不得发布。

## 验收标准

### 随从战斗隔离

- 随从不能入队；
- `fight`/`kill` 随从被服务端拒绝；
- `kill.js` 不再调用随从 `do_kill`；
- 随从不能进入副本复制房间；
- 普通 NPC、玩家组队和非随从战斗保持原行为；
- 安全区陪同、住宅展示和对白保持可用。

### 经营功能

- 旧 `home=1/2` 可以进入对应住宅等级；
- 住宅可以扩建、升级房间、增加仓库和设施；
- 无人值守有基础产出；
- 成员值守能显著改变产量、品质或事件；
- 四个职业都能排班、结算、领取和停止；
- 仓库满、资源不足、维护不足和任务冲突有清晰反馈；
- 停止、领取和离线结算不重复发奖；
- 维护不足先降效或暂停高阶生产，不删除成员。

### 成长和玩家收益

- 成员职业等级和培养记录可见；
- 不同成员配置产生不同经营结果；
- 家族声望、设施和成就能解锁实际内容；
- 玩家能获得材料、资金、丹药、训练和战前准备收益；
- 家族收益有投入和成长空间，但不生成战斗队友；
- 经营路线存在差异，后期可以继续扩建和调整。

### 兼容和稳定性

- 老随从技能、装备、背包和设置不丢失；
- 新旧存档都能读取；
- `household.version` 迁移幂等；
- 断线、重连、退出、重启后任务和待领取产物正确；
- 无住宅打开家族面板不报错；
- 服务器端不依赖前端状态做权限判断。

## 验证要求

根据实际修改范围执行最小充分验证：

- 修改的 CommonJS 文件执行 `node --check`；
- 前端修改执行 `npm run build`；
- 世界脚本通过服务加载或项目现有脚本检查方式验证；
- 涉及存档、继承和加载顺序时必须重启服务验证；
- 覆盖资源不足、权限不足、空住宅、空成员、仓库满、重复领取、离线结算、维护不足、转职和失败恢复；
- 记录无法执行的验证及原因，不得把未运行的测试写成通过。

## 禁止事项

- 不得把随从重新加入任何战斗逻辑；
- 不得只隐藏按钮而不做服务端拒绝；
- 不得删除或重命名 `temp.home`、旧随从存档和已发布资源路径；
- 不得把复杂家族数据塞入 `temp`；
- 不得为每个随从新增独立永久定时器；
- 不得直接编辑 `www/`，前端产物必须通过构建生成；
- 不得修改数据库、运行数据、`.env` 或生产公告；
- 不得引入新框架替代现有世界脚本、Dialog 和 Process 体系；
- 不得为了防刷把无人值守收益、家族成长或失败惩罚设计成不可玩；
- 不得顺手重构无关模块。
