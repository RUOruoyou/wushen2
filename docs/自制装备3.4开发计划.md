## 1. 目标与范围

### 1.1 目标

完成以下闭环：

```text
分解橙色装备 -> 元晶/属性晶石
-> 按地点制作全身自制装备 -> 查看自制状态
-> 添加词条 -> 洗练解锁 -> 升级词条/能力词条
-> 替换词条/改名 -> 精炼、镶嵌、穿戴、交易、分解
```

实现必须满足：

1. 新旧自制武器存档可继续加载、穿戴、精炼、镶嵌和分解。
2. 新增防具、饰品、暗器使用现有装备对象、背包和装备栏体系。
3. 单件分解、批量分解、自动拾取分解使用同一套产物计算和校验。
4. 词条修改在未穿戴和已穿戴状态下都不会造成属性叠加、残留或丢失。
5. 请求重复、材料不足、背包满、装备被锁定/镶嵌/不存在等错误均可恢复。
6. 前端沿用现有 `Dialog`、`Process`、`SendCommand` 和历史非严格 JSON 协议。

### 1.2 本计划不包含

- 不重写 `os/` 核心对象；除非存档或属性挂载验证证明扩展层无法实现。
- 不在规则未确认时自行决定数值、能力效果、返还比例或收费。
- 不删除或批量改写运行数据，不直接编辑 `data/`、日志、数据库和生成产物。
- 不在用户确认前发布玩家公告或部署生产环境。

## 3. 目标技术结构

### 3.1 配置与领域服务

建议在 `world/extends/` 增加自制装备扩展模块，集中提供：

- 属性、部位、槽位、费用和能力词条配置。
- 旧格式识别和新版状态规范化。
- `readState(item)`、`buildProp(item)`、`querySlots(item)` 等纯计算接口。
- 制作、添加、洗练、升级、替换、改名和能力设置的预检/提交接口。
- 分解产物计算接口，供单件、批量和自动分解复用。

模块名和具体文件路径在编码阶段按仓库动态加载规范确认；不得把配置复制到 `duanzao.js`、`fenjie.js`、前端多个文件中。

### 3.2 建议的自制装备状态

领域服务对外返回结构化状态，但首版持久化继续使用 `temp` 的扁平标量字段。原因是当前 `ITEM.prototype.format_temp()` 不能安全序列化嵌套对象；为此玩法修改全局序列化器会扩大到所有角色和物品存档。

建议持久字段如下；字段名可在阶段 A 调整：

```js
temp: {
    custom_version: 1,
    type: "ring",
    name: "自定义名称",
    wash_count: 25,
    affix_mz: 1,
    affix_str: 2,
    ability_skill: "",
    ability_category: "",
    ability_effect: ""
}
```

`readState(item)` 将这些字段规范化为按类别分组的运行时对象；类别由服务端属性配置推导，不在存档中重复保存。`writeState(item, state)` 只写白名单字段，并清理已知旧锻造字段，不遍历客户端提交对象。

实现约束：

1. `prop` 和 `original_prop` 只能由状态重建，不能作为唯一持久数据。
2. `name`、`type` 等旧平铺字段必须兼容读取；新写入统一使用新版结构。
3. 词条状态只保存稳定标识和等级，不保存嵌套对象、函数、连接、定时器或对象引用。
4. 若替换/分解需要历史投入，新增明确的可校验字段；不能通过遍历 `temp` 猜测属性。
5. `clone()`、`save_db()`、`load_db()`、排行榜快照和仓库转移都必须保留该状态。
6. 如果能力配置无法用扁平标量表达，优先保存稳定 `effectId` 并由服务端配置还原；不保存配置副本。

### 3.3 属性生效流程

统一为以下顺序：

```text
读取/规范化 temp
-> 校验部位和词条
-> 计算固定属性（洗练）
-> 计算词条属性（等级）
-> 计算精炼成长
-> 写入 original_prop
-> 调用 equipment.level_up(level) 得到 prop
-> 刷新 color_name/json/评分
```

已穿戴装备修改时：

1. 记录装备所在部位和当前属性。
2. 先从角色移除旧属性。
3. 原子修改状态并重建装备属性。
4. 重新挂载新属性，失败则恢复旧状态和旧属性。
5. 发送背包、装备栏和排行榜更新消息。

### 3.5 建议的消息与确认协议

服务端是规则唯一来源。前端只提交装备 ID、用户选择和服务端签发的一次性 token，不提交费用、属性数值、槽位上限或返还数量。

建议消息形状：

```js
{
    type: "dialog",
    dialog: "customEquipment",
    action: "state",
    itemId: "...",
    state: { /* 只读展示模型 */ },
    token: "..."
}
```

每个写操作分两步：

```text
preview(itemId, operation, selection)
-> 服务端校验并返回费用、结果摘要、状态指纹、短时一次性 token
-> commit(token)
-> 服务端重新定位装备、验证所有者/指纹/资源并原子提交
```

协议约束：

- token 必须绑定玩家、装备 ID、操作、选择、状态指纹、费用和过期时间。
- token 使用后立即失效；重复提交返回“本次操作已完成或已失效”，不能再次扣费。
- 装备状态、背包材料或黄金变化后，提交阶段重新校验，不信任预览时缓存。
- `state` 只包含前端展示需要的字段，不能暴露管理命令、函数名或内部对象引用。

## 4. 分阶段开发计划

### 4.1 里程碑总表

### 阶段 A：规则、配置和验证基线

**前置**：无。**产出**：规则冻结表、配置草案、测试样例。**不开放入口。**

任务：

1. 将附件矩阵转成机器可读配置草案，逐项映射 `os/const.js` 中实际属性键。
2. 标注底层已生效、仅显示可用、需要新增战斗消费逻辑的属性。
3. 对 `limit_mp/max_mp`、`diff_sh/diff_sh_per`、攻击速度、忙乱、释放/冷却时间做运行时调用链审计。
4. 计算各类槽位、升级上限、固定属性和分解样例的期望结果。
5. 设计旧平铺 `temp` 到新版状态的兼容读取规则。

验收门：

- 每个附件属性都有唯一内部键或被明确标记为“暂不支持”。
- 每个支持属性都有显示名、材料路径和生效消费者。
- 规则 R1-R12 全部有结论；未确认项不得进入后续编码。

### 阶段 B：状态模型与装备重建

**前置**：阶段 A。**涉及**：`world/obj/eq/cp.js`、`world/obj/eq/zb.js`、`os/item/equipment.js`（优先扩展层）。

任务：

1. 增加自制装备识别、版本化状态规范化和旧格式读取。
2. 为 `cp`/`zb` 统一设置名称、单位、部位、固定属性和制作来源描述。
3. 实现唯一 `buildProp()`，同时生成 `original_prop` 和当前 `prop`。
4. 接入精炼 0-12，逐项落实精炼成长白名单。
5. 验证 clone、保存、加载、重启、穿戴、卸下、装备栏消息和宝石保留。

验收用例：

- 旧 `eq/cp#sword` 存档加载后属性与改动前一致。
- 新版每种部位空状态、单词条、多词条、50/150 次状态均可重建。
- 反复穿戴/卸下和重启不会重复加属性。
- 精炼、镶嵌、锁定状态不被重建覆盖。

### 阶段 C：全身制作入口

**前置**：阶段 B。**涉及**：`world/cmd/obj/duanzao.js`、铁匠/成衣店/鉴宝阁地图和 NPC、`cp.js`、`zb.js`。

任务：

1. 把制作部位和地点权限做成白名单，不依赖前端隐藏按钮。
2. 铁匠铺开放武器；成衣店开放衣服、鞋、头部、披风、护腕、腰带；鉴宝阁开放戒指、项链、饰品、暗器。
3. 统一 10 元晶扣除、2-5 汉字名称校验、敏感词校验、背包容量检查和重复请求保护。
4. 创建后写入新版状态，调用 `on_reload`/属性重建并通知背包。
5. 对地点不存在或 NPC 不存在的环境提供明确阻断，不允许绕过地点权限直接制作。

验收用例：

- 每个地点只能制作允许部位，错误地点和错误部位均失败且不扣材料。
- 材料不足、背包满、名称非法、重复提交均不产生半成品。
- 新制作装备可立即查看、穿戴、精炼、镶嵌和保存。

### 阶段 D：重铸、洗练、升级和替换状态机

**前置**：阶段 B；规则 R5-R8 已冻结。**核心关键路径。**

#### D1 查看和添加词条

- 查看返回完整状态：洗练次数、固定属性、五类槽位、词条等级/上限、能力解锁状态、材料/黄金。
- 添加前校验部位矩阵、类别剩余槽位、重复属性规则、装备锁定/镶嵌/装备状态和材料。
- 预览与提交使用装备 ID、状态版本/指纹和一次性确认 token。

#### D2 洗练

- 每次消耗 1 元晶并递增 `washCount`。
- 处理 10、25、50、150 次解锁及最大升级等级。
- 按部位递增固定属性，不能把固定属性误记为可替换词条。
- 达到上限后明确提示，不允许溢出计数或重复解锁。

#### D3 词条升级

- 计算下一等级需求、材料路径、材料数量和升级后数值。
- 先预检所有资源，再一次性扣除和重建属性。
- 升级上限由洗练次数决定，不能仅由客户端传入等级决定。

#### D4 词条替换

- 预览新属性、旧属性、黄金费用和返还材料。
- 确认时重新检查装备指纹、黄金、材料、锁定、镶嵌和穿戴状态。
- 使用快照/回滚保证扣费、返还和属性变更原子完成。

#### D5 改名

- 沿用名称长度和敏感词校验。
- 根据 R11 扣除改名符或黄金；失败不改变名称。
- 刷新 `name`、`color_name`、`desc`、`json`、背包显示和存档。

验收用例：

- 每个操作分别覆盖成功、资源不足、权限失败、装备不存在、状态过期、重复确认、已穿戴、已镶嵌和已锁定。
- 模拟扣费后重建失败，确认旧状态、旧属性和资源均恢复。
- 洗练 0、10、25、50、150 次边界及重复操作结果符合冻结表。

### 阶段 E：能力词条

**前置**：阶段 D；规则 R10 已冻结。**不得先做 UI 再猜效果。**

任务：

1. 建立技能类型到装备部位的映射：武器/拳脚、暗器、内功、招架、轻功；双位置技能按第一位置。
2. 建立技能 ID 白名单和能力效果配置，不接受客户端任意技能键。
3. 将能力效果接入统一装备属性或技能查询钩子；优先复用现有 `releasetime_key`、`distime_key`、`expend_mp_per_key`，缺失效果另建受控扩展。
4. 25 次洗练后开放 1 条能力词条，不允许升级；明确是否允许替换及返还规则。
5. 能力词条在穿戴、卸下、重启、克隆、分解和交易中保持一致。

验收用例：

- 25 次前无法添加，25 次后只能添加 1 条。
- 错误技能类别、错误部位、未学技能或伪造技能 ID 均被服务端拒绝。
- 能力效果在装备穿脱前后只生效一次，重启后不丢失。

### 阶段 F：材料与分解统一

## 6. 数据迁移、兼容和回滚

### 6.1 兼容策略

1. 旧 `eq/cp` 平铺 `temp` 只读兼容，首次修改时规范化为新版状态。
2. 旧武器的名称、类型、已有属性等级、精炼等级、宝石和锁定状态不得丢失。
3. 新部位只能写新版状态，不允许生成无法被旧逻辑识别的半结构。
4. 迁移函数必须幂等：同一装备重复加载/保存不会重复添加属性或材料。

### 6.2 发布前备份与回滚

- 生产前备份数据库、角色存档和相关运行数据，记录备份时间与校验值。
- 先以只读校验脚本扫描旧自制装备数量、路径、`temp` 形状、精炼、宝石和穿戴关系。
- 采用“兼容读取 + 新写入”的渐进策略；首个版本不强制批量改写全部角色。
- 增加服务端入口开关：关闭时禁止制作、洗练、升级、替换、能力和改名等写操作，但继续按新版状态加载和穿戴装备。
- 只有尚未产生新版写入时才允许完整回退到旧代码；玩家已产生新版状态后，旧代码会忽略新词条，必须采用“关闭入口 + 保持新版读取 + 向前修复”，不能直接降级。
- 若出现属性重复或材料异常，停止入口、保留日志和备份，再按装备 ID 做定点修复，不直接全量清理。

### 10.2 最终存档与兼容契约

首版继续使用可被现有装备序列化器保存的扁平 `temp` 字段：

```js
{
    custom_version: 1,
    custom_state_version: 1,
    type: "ring",
    name: "自制戒指",
    wash_count: 25,
    fixed_level: 1,
    affix_str: 2,
    affix_legacy_str: 1,
    ability_skill: "huashanjianfa",
    ability_base: "sword"
}
```

- `affix_<key>` 保存词条等级；`affix_legacy_<key>` 只标记由旧存档兼容读取的旧数值公式。
- 旧 `name`、`type`、`sc` 和旧属性等级继续只读兼容；首次写操作会规范化到版本 1。
- 加载时忽略未知、当前部位不允许或能力部位不匹配的持久字段；洗练次数限制为 0-150，固定属性和普通词条等级限制为 1-6，不把越界值直接挂到角色属性。
- `original_prop`、当前 `prop`、名称、描述和操作入口都由状态重建；克隆、保存/读取、精炼、宝石和锁定沿用原装备机制。
