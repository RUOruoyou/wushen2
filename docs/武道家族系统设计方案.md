# 武道家族系统设计方案

> 文档状态：设计方案，尚未进入代码实现
>
> 适用项目：wsmud2
>
> 目标：在保留现有门派、随从、住宅、任务和存档兼容性的前提下，把随从从战斗队友转为家族成员，把住宅从一次性购买的房间转为可扩建、可生产、可成长的武道家族经营基地。

## 1. 总体结论

本方案的核心不是给现有随从增加更多战斗技能，而是重划职责边界：

1. 随从永久退出战斗闭环，不再加入玩家战斗队伍，不再响应自动击杀，不再被玩家命令比试或击杀。
2. 随从成为有职业、资质、忠诚、疲劳、经验和成长记录的家族成员。
3. 住宅由 home=1/2 的单间/豪宅标志升级为住宅等级、房间设施、生产队列、仓库和家族声望；旧 home=1/2 继续保留兼容。
4. 现有 wk、caiyao、diaoyu 是实时个人工作命令，不能原样承担离线经营。新系统在 world/extends/household/ 中建立统一任务调度器，rel 只作为兼容入口。
5. 玩家有玩家本人、家族成员、住宅家族三条成长线，可以获得收入、材料、丹药、训练机会、授课声望和非战斗提升，但不能让家族成员直接替玩家打怪。

这套结构具备模拟经营的核心要素：有限空间、设施建设、资源投入、生产周期、离线结算、人员配置、随机事件、维护成本、长期解锁和经营成就；同时仍然使用本项目已有的世界脚本、命令、房间、物品、存档和非严格 JSON 消息体系。

## 2. 基于实际代码的现状分析

### 2.1 现有可复用基础

| 领域 | 当前代码 | 结论 |

| 随从对象 | os/char/follower.js 的 FOLLOWER、FOLLOWER.STORES、FOLLOWER.SAVE | 已具备独立对象、技能、装备、背包、状态和持久化能力 |

| 工作命令 | world/cmd/action/wk.js、caiyao.js、diaoyu.js 通过 set_state、心跳和 on_enter 结算 | 可复用公式和物品概念，不能原样做离线任务 |

| 关系弹窗 | src/dialog/relation.js 显示 data.fls 并发送 rel 工作命令 | 保留摘要兼容，工作操作转家族面板 |
| 消息分发 | src/process.js 将 dialog 消息交给 Dialog | 新增 household 弹窗，不另造前端框架 |

### 2.2 当前住宅为什么不够像经营系统

现有住宅购买后主要是固定房间和固定功能：

- 没有可规划的空间、房间等级、容量和维护费。
- 随从工作是实时 state，收益直接进入随从背包或经验。
- 没有生产队列、家族仓库、离线结算、订单和经营事件。
- 玩家没有“投入资源、安排人员、等待产出、处理风险、继续扩建”的决策循环。

因此扩展重点应是经营底座，而不是简单增加工作按钮。

## 3. 系统边界

### 3.1 FAMILIES 与 HOUSEHOLD 分离

FAMILIES 继续负责门派归属、门派技能、师门任务、门派称号、门派区域和武学权限。不能把家族等级写入 FAMILIES，不能用 temp.family 覆盖家族数据。

新增 HOUSEHOLD 表示玩家经营的武道家族，统一提供：

- HOUSEHOLD.ensure(user)：为旧角色补齐默认数据。
- HOUSEHOLD.view(user)：生成家族面板数据。
- HOUSEHOLD.assign(user, followerId, job, options)：安排职业。
- HOUSEHOLD.stop(user, followerId)：停止任务并结算。
- HOUSEHOLD.collect(user, slot)：领取产出。
- HOUSEHOLD.upgrade(user, target)：升级住宅、设施或仓库。
- HOUSEHOLD.tick(user, now)：在线和离线结算。
- HOUSEHOLD.save(user)：保存可序列化家族数据。

HOUSEHOLD 不直接处理玩家战斗，不调用 do_kill、fight 或 team with。

### 3.2 战斗队伍与家族成员分离

team.js 继续服务玩家组队、副本和拾取分配。随从不再作为队伍成员：

- team with <随从> 返回“家族成员不参与战斗，请在家族面板安排工作”。
- 随从可以在住宅和安全区域展示、对话或短暂陪同，但不写入 me.team。
- 随从不能进入副本、战斗地图或需要队伍的活动。

## 4. 随从永久退出战斗

### 4.1 禁止规则

以下行为全部禁止：

- 对随从执行 team with、fight、kill。
- 随从因玩家 kill 命令自动调用 do_kill。
- 随从因 auto_kill 设置加入战斗。
- 随从跟随玩家进入副本复制房间。

这必须是服务端规则，不是只隐藏按钮。命令、对象、组队、房间移动、自动战斗和前端均要校验。

### 4.2 文件级修改方案

| 文件 | 修改 | 原因 |
| --- | --- | --- |
| os/char/follower.js | query_mastercommands 移除 fight、team with；query_commands 移除 fight、kill；新增 family_member 标记 | 对象级统一边界 |
| os/char/follower.js | on_teamin 拒绝或不再执行；on_master_leave 禁止副本跟随，保留安全区表现 | 防止旧路径绕过 |
| world/cmd/comm/team.js | team_with、team_add、team_reply 识别并拒绝 FOLLOWER | 切断所有入队入口 |
| world/cmd/battle/kill.js | 目标是家族成员时拒绝；遍历 team 时跳过 family_member | 消除 do_kill 调用链 |
| world/cmd/comm/rel.js | 停止和旧工作别名转 HOUSEHOLD，不再调用 target.do_command | 统一任务调度 |
| src/dialog/relation.js | 移除战斗按钮，工作按钮打开家族面板 | 不显示失效命令 |

首阶段不要重写 os 历史代码。先在 world/extends/household/ 和命令入口加保护，完成调用链验证后再做最小对象覆盖。

### 4.3 允许的非战斗表现

- 在住宅中展示姓名、职业、疲劳、心情和工作。
- 在住宅中触发对白、拜访、节日事件和家族任务。
- 在安全地图短暂陪同，不加入队伍、不产生仇恨、不参与伤害计算。
- 接受工具、装备和礼物；装备只影响生产、容量或事件，不影响战斗。

## 5. 存档与迁移

### 5.1 现有存档限制

USER.loadData 在 os/char/user.js 中读取 role.data，已有 prop、items、stores、eq、settings、skills、temp、follower 等字段；USER.getData 负责历史格式序列化。

FOLLOWER.save 已保存数值属性、背包、技能、temp、settings 和装备。复杂的家族生产数据不能放进 follower.temp，因为 format_temp 适合简单临时字段，不适合稳定嵌套对象。

### 5.2 新增顶层 household

建议角色数据增加：

    household: {
        version: 1,
        level: 1,
        exp: 0,
        renown: 0,
        treasury: 0,
        upkeepDue: 0,
        facilities: {},
        members: {},
        jobs: {},
        queue: [],
        warehouse: {},
        achievements: {},
        events: {},
        lastTick: 0
    }

只保存数字、字符串、布尔值、数组和普通对象，不保存 USER、FOLLOWER、ROOM、定时器、函数或循环引用。缺失字段由 HOUSEHOLD.ensure 补齐，version 用于迁移。

### 5.3 home=1/2 映射

| 旧值 | 旧含义 | 新系统初始化 |
| --- | --- | --- |
| 缺失或 0 | 无住宅 | 不创建生产家族，显示建宅引导 |
| 1 | 精致型单间 | household.level=1，基础居所、1 个成员位 |
| 2 | 豪华型住宅 | household.level=2，院落、花园、练功房、炼药房、基础仓库 |

home 仍由现有管家、房契和 USER.query_home 使用，HOUSEHOLD 只把它作为所有权兼容来源，不替换 home。

### 5.4 存档修改文件

| 文件 | 修改方式 | 原因 |
| --- | --- | --- |
| world/extends/char/user.js | 延续现有包装 loadData/getData，读取和写入 household | 减少 os 核心改动 |
| os/char/user.js | 仅在扩展包装无法覆盖时增加读写 | 历史核心风险高 |
| os/char/follower.js | 保留旧随从存档，职业数据从 household.members 读取 | 兼容旧技能、装备和背包 |
| world/extends/world.js | startup 初始化，heart_beat 做轻量调度 | 对齐现有世界生命周期 |

## 6. 家族数据模型

### 6.1 家族主体

| 字段 | 说明 |
| --- | --- |
| version | 存档版本 |
| level、exp | 家族等级和经营经验 |
| renown | 武馆授课、事件和订单声望 |
| treasury | 家族资金，与玩家 money 分开 |
| upkeepDue | 维护费状态 |
| facilities | 房间等级、耐久和解锁 |
| members | 成员职业、成长和关系 |
| jobs、queue | 进行中的任务和生产队列 |
| warehouse | 材料、药材、丹药、成品 |
| achievements | 家族、成员、设施和武馆成就 |
| events | 事件冷却、分支和历史 |
| lastTick | 上次离线结算时间 |

### 6.2 成员模型

基础战斗属性仍保存在 FOLLOWER，经营属性放入 household.members[id]：

    {
        id: "follower_id",
        role: "worker",
        job: "mining",
        jobLevel: 1,
        exp: 0,
        aptitude: 0,
        loyalty: 50,
        mood: 70,
        fatigue: 0,
        traits: ["勤勉"],
        specialty: "ore",
        tools: {},
        assignedFacility: "yard",
        lastRewardAt: 0,
        lifetimeOutput: {},
        milestones: {}
    }

- jobLevel 是职业等级，不等于武学 level。
- aptitude 决定成长上限和职业偏好。
- loyalty 影响离岗、事件和协作效率。
- mood 影响短期产能，不能转成战斗数值。
- fatigue 通过休息和轮班降低。
- traits 形成成员差异，例如勤勉、节俭、药香、善教、谨慎。
- lifetimeOutput 和 milestones 用于养成成就，换职业不清零。

### 6.3 任务模型

任务独立于 follower.state：

    {
        id: "job_001",
        memberId: "follower_id",
        job: "mining",
        facility: "yard",
        startedAt: 0,
        lastSettledAt: 0,
        endAt: 0,
        input: {},
        pendingOutput: {},
        status: "running",
        repeat: true
    }

状态至少有 running、paused、completed、failed、awaiting_collect。结算必须幂等，同一时间不能重复发放材料、资金、经验或声望。

### 6.4 家族仓库

- warehouse.materials：矿石、药材、种子、燃料、木材。
- warehouse.products：丹药、成品装备、授课凭证和订单成品。
- warehouse.capacity：由仓库和设施等级决定。
- warehouse.ledger：限制长度的生产、消耗和出售记录。

仓库满时任务暂停或进入待领取，不静默丢失产物。

### 7.3 住宅地图

现有 world/map/home/yuanzi.js、danjian.js、woshi.js、liangong.js、lianyao.js、huayuan.js、store.js 继续作为房间身份。

新增建议：

- world/map/home/kuangchang.js：矿场。
- world/map/home/yaopu.js：药圃或种植区。
- world/map/home/wuguan.js：家族武馆。
- world/map/home/xuetang.js：学堂。
- world/map/home/gongfang.js：工坊。

新房间只负责环境、出口、进入权限、描述和动作入口；产出、费用、队列、结算统一放 HOUSEHOLD。

## 8. 四类职业

### 8.1 挖矿

家族矿场需要铁镐、矿工成员和目标矿脉。任务周期生成矿石、宝石和矿脉经验，产物进入仓库，可出售、用于工坊订单、装备材料或升级矿场；高级矿脉有塌方、工具损耗和疲劳事件。

与现有 wk 的关系：

- 复用工具效率、经验和矿石品质思想。
- 不调用 target.do_command("wk")，不依赖随从实时位于 home/huayuan。
- 玩家本人继续在 yz/kuang 或住宅花园使用原 wk。
- 家族矿工用离线任务，不向随从直接发玩家经验。

收益是矿石、宝石、家族经验和少量家族资金，成员职业经验不提高玩家战斗等级。

### 8.2 种植

种植补齐当前花园的经营深度，必须有种子、地块、成长阶段和收获季：

- 地块状态：空闲、播种、生长、成熟、枯萎。
- 种子：普通药草、灵谷、花卉、特殊事件作物。
- 周期：短周期日常材料，长周期稀有配方。
- 影响：花园等级、种植等级、天气、灌溉和肥料。

玩家获得种子，分配地块和成员，等待多个阶段后收获。产物进入仓库，可出售或交炼药房。种植提供“今天播种、明天收获”的稳定经营节奏。

### 8.3 炼药

复用现有 home/lianyao、can_lianyao、world/cmd/obj/lianyao.js 和 world/skill/knowage/lianyao.js 的药材、配方和技能概念，但家族炼药改为队列：

1. 选择配方、数量和炼药成员。
2. 校验药材、炉位和燃料。
3. 生成队列，不立即写入玩家背包。
4. 结算成功率、品质、副产物和失败损耗。
5. 成品进入家族仓库，可领取、出售、交订单或供玩家使用。

现有玩家炼药命令继续实时执行；家族成员不执行玩家命令链。

### 8.4 授课和武馆

武馆是武道家族的特色，也是家族资金和声望的主要来源：

1. 选择基本功、兵器入门、内功启蒙、实战礼法等课程。
2. 设置收费、招生规模和授课成员。
3. 按周期收取学费，产出家族资金和武馆声望。
4. 学员满意度受教习、课程、设施和事件影响。
5. 声望解锁高级课程、订单和 NPC。

教习属性包括 teaching、reputation、specialty、patience。武馆不产出战斗队友，玩家获得的是课程研究、学堂和练功房辅助、声望服务以及可支付学习和升级的资金。

## 9. 任务调度和离线结算

### 9.1 为什么不能只用 follower.state

wk、caiyao、diaoyu 的 state 依赖心跳、environment、工具和在线对象，退出或移动时状态可能清理；经营系统必须支持玩家下线推进、重启恢复、延迟领取、仓库满、维护不足、疲劳和暂停。

因此 state 只能作为当前展示状态，不能作为经营数据唯一来源。

### 9.2 结算时机

HOUSEHOLD.tick 在以下时机调用：

1. 玩家登录完成后。
2. 打开家族面板时。
3. 执行家族命令时。
4. WORLD.on_heart_beat 的轻量在线轮询中。
5. 玩家退出保存前。

不要为每个随从建立独立定时器；按用户统一结算，避免泄漏、重启丢失和重复奖励。

### 9.3 公式和边界

    有效效率 = 基础效率 + 职业等级 + 资质 + 设施 + 工具/配方 + 心情 - 疲劳 - 维护不足
    结算次数 = floor((now - lastSettledAt) / 周期)

结算必须：

- 限制最大离线时长，例如 72 小时。
- 仓库满时立即暂停或进入待领取。
- 每个任务记录 lastSettledAt 和唯一 id。
- 写入前检查任务和时间，打开面板不能重复发奖。

### 9.4 维护费

维护项目包括房间、矿场工具、炼药燃料、武馆宣传、成员伙食和休息。维护不足时先降低高阶队列效率，再暂停高耗生产，最后才触发设施停用事件；基础生产和成员休息尽量保留。不得删除随从或生产物，停业和恢复应可逆。

## 10. 三条成长线

### 10.1 玩家成长

玩家仍通过 exp、pot、skills、equipment 和门派系统成长。家族提供：

- 武馆学费、订单和出售产品产生的资金。
- 矿石、药材、作物和丹药。
- 工具和仓库服务。
- 学堂研究、练功房和非战斗修炼便利。
- 声望解锁商人、教习、订单和住宅事件。

禁止用家族产出固定攻击、防御、气血百分比替代玩家修炼。

### 10.2 成员成长

成员有职业等级、资质、特性、忠诚、心情、疲劳、培训和职业转型。成员可以从学徒成长为高级矿工、首席药师或名馆教习，并保留产出记录、事件历史和里程碑。

### 10.3 家族成长

家族等级和声望解锁新房间、地块、工具、配方、队列、仓库容量、武馆课程、订单、NPC、称号、住宅外观和成员服饰。家族等级不等于玩家等级。

### 10.4 成就

| 类型 | 示例 | 奖励 |
| --- | --- | --- |
| 经营成就 | 收获 1000 份作物、完成 100 次订单 | 声望、家具、称号 |
| 成员成就 | 成员职业 10 级、忠诚 100 | 特性、家族被动 |
| 设施成就 | 全部房间 3 级、仓库扩建 | 外观、容量、队列 |
| 武馆成就 | 培养 100 名学员、开设高级课程 | 资金、课程、教习事件 |

奖励优先是解锁、展示、经济便利和非战斗能力，避免成为战斗数值外挂。

## 11. 家族如何提升玩家

### 11.1 直接收益

- 资金：减轻日常现金压力。
- 材料：减少重复采集时间。
- 丹药：提高修炼准备效率。
- 工具：提升玩家本人 wk、caiyao、diaoyu 效率。
- 仓库：降低物品管理压力。

### 11.2 间接收益

- 练功房提供有限的修炼效率或疲劳恢复。
- 学堂解锁生活技能课程和配方。
- 武馆声望解锁商人、订单和公共服务。
- 成员协作形成矿工、药师和教习之间的生产加成。

### 11.3 明确不提供

- 随从自动打怪、刷副本或自动拾取战斗奖励。
- 直接复制玩家武学代替玩家战斗。
- 无限叠加的攻击、防御、气血和命中加成；有限的课程、药剂和宴席效果可以作为家族高阶内容。
- 用家族生产完全替代玩家探索、战斗、任务和门派成长。

## 12. 经济闭环

    玩家资金/材料
        -> 房间、工具、种子、燃料、成员培养
        -> 成员生产和武馆授课
        -> 材料、丹药、成品、资金、声望
        -> 玩家修炼、订单、住宅升级、成员培训

必须设置设施升级、工具耐久、燃料、种子、药材、宣传费、培训费和特殊订单材料等消耗。高级产出应与玩家探索、任务或副本材料建立有限交叉，防止家族成为无限印钞机。

## 16. 玩家是否有真实培养和养成成就

有，且必须通过可观察差异体现：

1. 招募成员时选择职业或发展方向。
2. 资质、特性和性格让不同成员有不同价值。

5. 每名成员保留生产记录、事件历史和里程碑。
6. 家族记录首件极品丹药、第一位高级学员、首个大型订单等纪念成就。
7. 玩家因培养结果选择矿场、药圃、武馆或均衡发展，而不是所有住宅同质化。

奖励优先为特性、配方、效率、称号、外观、声望和经营便利；少量非战斗属性提升可以存在，但成员不是第二套战斗角色。

### 17.2 效率提升

### 17.3 解锁提升

## 22. 方案拷问与最终取舍（自答版）

本章把方案放进连续的设计拷问中。每轮只保留一个最贴合当前项目的推荐，并给出明确答案，避免实现时重新回到模糊的“可以都做”状态。

### 第 1 轮：为什么必须培养成员，不能只升级建筑？

**推荐：设施提供基础生产，成员把基础生产变成高质量、可扩展的家族产业。**

如果成员只是给建筑提供百分比加成，最终一定会退化成“升级建筑即可”，随从培养没有存在理由。成员应当承担建筑无法替代的三类职责：职业专精（矿工、药师、教习的不同产出）、现场决策（处理订单和随机事件）以及关系网络（解锁特定配方、学徒和 NPC）。

因此设施定义可用岗位、队列容量和基础产出；没有成员时仍可以低效率运转，避免住宅在玩家离线或成员临时调岗时完全失去生命力。成员的职业等级和特性写入 `household.members`，而不是继续依赖随从实时 `state`。成员值守后才会出现专精产物、品质提升、订单处理和特殊事件。

**结论：**玩家培养成员是打开经营上限和内容差异的必要投入，不是维持最低产出的门槛。

### 第 2 轮：无人值守时是否保留自动收益？

**推荐：无人值守保留基础产出，成员值守决定效率和内容上限。**

住宅不应该因为一次临时离岗就变成死建筑。成员离岗后，设施按较低效率继续生产普通材料；高级配方、品质加成、订单和随机事件暂停。住宅仍然会消耗最低维护费，并让成员恢复疲劳。这样玩家有持续收益，也有充分理由回来排班和培养成员。

该规则也适合现有 `rel <随从> <工作>` 的迁移：旧命令不再让随从进入实时工作状态，而是创建一个有明确开始时间和结束时间的任务。

**结论：**保留基础收益维持经营连续性，把真正的选择和高价值收益留给成员排班，而不是用停产制造压力。

### 第 3 轮：随从退出战斗后，玩家为什么还愿意保留旧随从？

**推荐：旧随从全部转为可培养成员，保留其身份和资产，并给出一次免费职业定向。**

旧随从的技能、装备、背包和关系记录不删除；迁移时生成初始资质和职业倾向，玩家可以在首个家族季免费选择职业。成员不再进入 `me.team`，但会带来材料、收入、授课声望、训练机会和住宅事件。

补偿不能直接改成战斗属性，否则会绕回原来的战斗外挂。玩家感受到的收益应是节省准备时间、提高资源质量、解锁训练内容和降低经营风险。

**结论：**退出战斗是职责重置，不是旧随从价值清零。

### 第 4 轮：家族会不会替代玩家刷资源和探索？

**推荐：家族可以提供从基础到中阶的完整供应链，稀有战斗掉落和关键探索仍由玩家主导。**

挖矿、种植和炼药可以产出基础及部分中阶材料，经过设施、配方和成员专精后还能制作有价值的成品；武馆可以提供稳定现金流和训练资源。副本核心掉落、顶级装备材料和关键剧情资源仍应由玩家探索获得，让经营与战斗互相需要，而不是互相排斥。

家族产出通过仓库容量、维护费、队列数和离线结算上限自然形成节奏；高级材料采用加工、订单和成员专精逐步转化，而不是无成本凭空生成。

**结论：**家族是稳定供应链、成长加速器和玩家战前准备的重要来源，但不替玩家完成探索。

### 第 5 轮：首版职业是否过多，如何避免系统失控？

**推荐：首版只落地四个职业，统一任务模型。**

首版固定为挖矿、种植、炼药、授课/武馆。四者共享 `HOUSEHOLD.assign/tick/collect`，只通过职业定义表配置消耗、时长、产出和事件。钓鱼等旧工作保留兼容提示，待统一调度器稳定后再接入。

四个职业形成不同经营方向：挖矿偏材料供应，种植偏周期和仓储，炼药偏加工与品质，授课偏现金流和声望。这样既有差异，又不会为每个工作复制一套实时心跳逻辑。

**结论：**先做少量但互相有供应关系的职业，不用数量掩盖循环深度不足。

### 第 6 轮：离线结算如何防止刷取、重复领取和时间异常？

**推荐：按用户统一结算，使用统一时间戳、可调离线时长和幂等领取。**

存档只记录 `last_tick_at`、任务开始/结束时间、已结算批次和待领取产物，不为每个随从建立定时器。登录、打开家族面板、分派、停止和领取前统一调用 `HOUSEHOLD.tick(user, now)`。

单次离线结算采用可配置上限，首版建议 72 小时，后续可根据经济数据调整；服务器时间回拨时取不小于上次结算时间的值；领取操作写入批次 ID，重复请求只能返回“已领取”。仓库满时产出留在任务待领取区，不直接丢弃或溢出背包。

**结论：**离线是结算方式，不是另一套奖励规则；所有奖励必须可追踪、可重放、不可重复。

### 第 7 轮：住宅扩建怎样才不是单纯加数值？

**推荐：扩建逐步增加空间，早期有取舍，后期允许玩家建设完整家族。**

住宅等级增加房间槽位和基础容量，但早期房间有限，玩家需要优先建设矿场、药房、药圃或武馆。随着等级提升可以补齐更多设施，不强迫玩家永久锁定某条路线。例如矿场升级增加矿石种类和工具槽，药房升级增加炼制队列，武馆升级增加学员席位。

设施存在维护费和前置材料，扩建后还会增加成员伙食、工具维护或宣传成本。玩家在发展阶段可以选择“矿场+药房”“药圃+炼药房”或“武馆+学堂”等组合；后期即使补齐设施，不同成员配置和升级顺序仍会形成差异。

**结论：**空间和维护成本制造经营决策，分支布局制造长期差异。

### 第 8 轮：玩家能否从家族获得真实提升？

**推荐：提供非战斗效率、成长资源和战前训练，让家族成为玩家成长的一部分，但不生成战斗队友。**

玩家可以从家族获得四类明确提升：

1. 资金和基础材料，减少重复采集时间；
2. 炼药和种植提供有上限的恢复品与修炼辅助品；
3. 武馆和学堂提供训练课程、技能熟练度或任务线入口；
4. 住宅设施提供休息、仓储、制作和订单效率。

这些提升仍需投入、容量和时间，并与 `temp.family` 的门派武学权限分离。家族可以通过练功房、武馆课程、炼药和短期宴席提供修炼效率、临时状态、技能熟练度和战前准备；长期属性成长可以作为高阶家族成就或课程奖励，但不能由随从直接替玩家出战，也不能无限叠加。

**结论：**家族能让玩家真实变强，并且变强的方式来自经营投入和成员培养，而不是多一个战斗单位。

### 第 9 轮：疲劳、忠诚和失败会不会让经营变成惩罚？

**推荐：状态影响效率和事件，不删除成员、不永久锁死职业。**

疲劳降低产出效率，心情影响事件概率，忠诚影响离岗和订单风险；这些状态都能通过休息、伙食、对话、培训和住宅设施恢复。生产失败只损失本批次部分投入或降低品质，不直接损毁成员。

成员可以转职，但需要时间、费用和培训空档；高忠诚成员转职成本更低。这样培养有长期意义，同时不会因为一次排班失误让玩家失去数周进度。

**结论：**经营风险必须可预期、可恢复，惩罚用于产生决策而不是制造弃坑点。

### 第 10 轮：如何保证随从永远不会绕过战斗禁令？

**推荐：服务端多层拒绝，前端只做辅助隐藏。**

对象层在 `os/char/follower.js` 移除战斗菜单并拒绝 `on_teamin`；命令层在 `world/cmd/comm/team.js` 和 `world/cmd/battle/kill.js` 拒绝入队、攻击和自动击杀；移动层禁止进入副本复制房间；前端 `src/dialog/relation.js` 只展示家族岗位，不发送旧战斗命令。

即使用户伪造 WebSocket 命令，服务端仍按 `family_member` 标记拒绝。玩家攻击其他目标时，`kill.js` 遍历队伍也必须跳过家族成员，避免旧 `do_kill` 调用链残留。

**结论：**“不能战斗”是对象、命令、战斗和地图四层不变量，不是 UI 选项。

### 第 11 轮：旧角色和旧住宅如何无感迁移？

**推荐：保留旧字段，新增版本化顶层 `household`，只在访问时惰性补齐。**

`temp.home=1/2` 继续代表旧住宅类型，并映射为 `household.level=1/2`；没有住宅的角色不创建生产数据。旧随从存档继续由 `FOLLOWER.STORES/SAVE` 读取，家族成员资料在 `household.members` 增补，不能把复杂嵌套对象塞进 `temp`。

迁移函数必须幂等：重复登录、重启或热更新不会重复发放房屋、材料和职业奖励。新增字段缺失时按默认值读取，版本升级只追加可回滚的数据，不删除旧字段。

**结论：**兼容优先于“清理旧模型”，先让旧角色安全进入新循环，再逐步替换旧入口。

### 第 12 轮：什么标准证明它已经是模拟经营，而不是工作按钮集合？

**推荐：用完整经营闭环作为验收门槛。**

必须同时存在以下链路：住宅扩建提供空间，设施消耗资源，成员排班启动生产，任务经过时间结算，产物进入家族仓库，维护费和状态形成成本，订单和事件要求玩家做选择，声望和成就解锁下一层内容，家族产出反过来提升玩家的修炼与探索效率。

如果只能“点击工作并领取固定奖励”，即使职业名称很多，也不算模拟经营。首版验收至少要证明：不同成员配置产生不同结果；离线重登不重复奖励；维护不足会让高阶生产降效或暂停；玩家能从矿场、药房、武馆或均衡路线中做出有代价的选择。

**结论：**经营感来自资源、人员、时间、风险和扩建之间的连续决策，而不是界面数量。

### 拷问后的统一实现决策

综合以上答案，首版实现应遵守以下核心取舍：

1. 随从不进入任何战斗队伍和自动击杀链路。
2. 设施没有值守成员仍可基础生产；值守成员决定效率、品质和高级内容。
3. 四个首发职业共用一个可离线结算的任务调度器。
4. 家族提供稳定且有成长空间的资源、现金流和训练收益；顶级战斗掉落仍由玩家探索获得。
5. 成员、住宅、玩家三条成长线互相作用，但不合并门派数据。
6. 所有失败和状态惩罚可恢复，不能删除成员或永久锁死路线。
7. 旧 `home`、随从、关系弹窗和命令入口必须有兼容迁移或明确拒绝提示。

这组决策可以直接作为后续编码的评审清单：新增职业、设施或奖励优先检查是否增加了玩家选择、成员差异和经营乐趣；只有触及战斗边界、存档一致性或奖励重复时，才需要加入硬性限制。
